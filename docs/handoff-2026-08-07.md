# Handoff — 2026-08-07

Written for whoever picks this up next, including a later version of me. The
measurements matter, but the mistakes matter more: five of the six wrong turns
below share one shape, and recognising it early would have saved most of a day.

Production is `0a7fb58b`. Local suite 352/352, `npm run check` green.

---

## The failure mode that cost the most

**Six times today a conclusion was drawn from an indicator that had not itself
been checked.** Five cost detours. The sixth wrote to the production database.

| # | The indicator | What it "showed" | What was true |
| - | - | - | - |
| 1 | bracket names vs field names | "the thin path carries 0 of 13 brackets" | the two vocabularies differ; a mapping sits between them |
| 2 | `CANONICAL_FIELD_NAMES` membership | "`subject` is missing" | it is carried as `subjects` |
| 3 | a hand-built fixture | "`PSA 10` is dropped from titles" | the fixture bypassed the parser that derives `grade` |
| 4 | raw grammar-order strings | "`[Variant]` is unreachable" | it is carried as `release_variant` |
| 5 | absence of `ingest_*` keys in a row | "the request took the direct endpoint" | those keys are added AFTER the row is written |
| 6 | `dataset_disposition` **column** | "the OWNER auto-marking rule is broken" | the marker lives in the nested `writer_feedback` field, by design, with a test asserting the column stays `OBSERVE_ONLY` |

Number 6 is the one to learn from. The rule had worked correctly since 2026-08-02
— 51 rows prove it. Acting on the misreading meant two unnecessary writes to an
append-only-by-design table (through its admin escape hatch), then a third to
undo them. Net value: zero. Net risk: not zero.

**The habit that prevents all six:** before believing an instrument, feed it a
case whose answer you already know. When a probe reports something extreme —
"0 of 13", "the rule never fires" — suspect the probe first. Extreme readings
are far more often broken instruments than broken systems.

A second, related rule earned today: **an indicator built from absence proves
nothing until you know when the thing would have been written.** Number 5 sent
the client-timing fix to the wrong endpoint entirely.

## What shipped

**CSM conformance.** `scripts/verify-founder-decisions-20260804.mjs` went from
22 to 23 clauses, all asserted against running code. Added COS-21's canonical
editable field list, verbatim and in order, with implementation terms
(`serial_number`, `print_run_*`) explicitly barred.

**Three TCG/Lot brackets the thin path could not emit.** `special_stamp` and
`description` had no schema field, and the Composer filters the grammar order by
the fields it holds — so they were absent from the order and nothing reported a
bracket missing. Both are canonical CSM names (COS-21, COS-23) and both had to
reach `toResolvedFields` as well, or a title could claim a printed `1st Edition`
its stored identity never had.

**COS-14's Lot expression.** The Lot bracket folds Manufacturer, Product and Set
into one, and a Set extending neither was dropped — against the decision's own
approved example. On the frozen 100-card cohort the baseline reproduced
byte-identically and the delta moved +0.012349 → +0.013562, turning the one loss
into a win (14/1/85 → 15/0/85, p 0.00098 → 0.000061).

**`Lotx1` — found in production data.** Three lot compositions, two of them a
single card, all three the same dual-signature card, which the schema names
explicitly as NOT a lot ("several names on one card"). The count was right and
the grammar was wrong, and the title asserted the misreading. The marker is now
withheld below two, and `lot_single_card` tells the caller — a different state
from `lot_quantity_unresolved`, where the count is unknown rather than known and
contradictory.

**Suites that could never run.** The two CSM PostgreSQL harnesses invoked
`pg_ctl` with the caller's environment; with neither `LC_ALL` nor `LANG` set —
the default in a non-login shell on macOS — the postmaster refuses to start and
`pg_ctl` reports nothing of its own, so they read as a missing PostgreSQL. They
skip on CI for want of a server. Between the two they had not run in a long
time, and they were hiding a real defect: `buildCsmStageRows` wrote an
`evidence` key that `csm_marketplace_structured_check` forbids, which would have
failed every atomic write. CI now puts PostgreSQL 17+ on PATH so the gate can
fail.

**Latency instrumentation, and the three ordering defects behind it.** Client
stage timings reached production three deploys in a row without landing. The
cause was ordering, in three places, all the same shape: `runDirectCsmAsset`
writes `latency_stages_ms` to the session itself, so anything merged into the
result afterwards decorates the HTTP response and never reaches a column.

- ingest decoded the client's timings from its header and merged them after the
  call — **this is the one that mattered; production takes this path**
- the direct endpoint's prologue stages had never landed once
- `ingest_body_bytes` was response-only

`handler_total_ms` and `ingest_total_ms` stay response-only on purpose: each
measures the request that contains the persistence.

## What the measurements say

Production, 2026-08-07, `gpt-5.6-luna` at `effort: low`:

| Upload bytes | Path | Blocking storage upload | provider_ms |
| --: | -- | --: | --: |
| 241,378 | ingest | — | 6,538 |
| 486,619 | ingest | — | 7,071 / 7,133 |
| 3,052,596 | ingest | — | 10,397 |
| 7,444,587 | **direct** | **11,390–12,224** | 10,781 / 11,407 |

The divide is `STORAGE_UPLOAD_RELAY_MAX_BYTES` (3.2MB). Above it recognition
blocks on the storage upload; below it the bytes ride inline. A 7.4MB card is
~26s end to end against ~6.7s for a 241KB one — the same pipeline, four times
the wait.

**Provider time scales with image size too** (6.5s → 11.4s), even though
`detail: "high"` bounds what the provider consumes. Large images cost at both
ends, so a bounded derived image saves twice.

Run-to-run noise on identical input: provider ±0.6s, storage ±0.8s. Differences
smaller than that are not findings.

### Model variance is mostly definition debt, not perception

14 real cards, same image through both arms:

| | Control (original vs original) | Original vs 1600px JPEG |
| -- | --: | --: |
| serial | 3 | 2 |
| card_number | 2 | 2 |
| card_name | 8 | 5 |
| set | 4 | 6 |
| **total field disagreements** | **21** | **20** |
| cards agreeing on every field | 4/14 | 2/14 |

Bytes: 40,757,108 → 6,745,152 (16.5%).

**Downscaling does not degrade fine print.** But the headline is the control:
with *nothing changed*, only 4 of 14 cards agreed on every field. `set` and
`card_name` account for 12 of 21 disagreements, always the same shape — one
string moving between the two fields. Only 2 of 14 were genuine misreadings.

Sampling parameters cannot help: `gpt-5.6-luna` rejects `temperature`, `top_p`
and `seed` (400, "not supported with this model"). The remaining lever is the
definition, which is what COS-23 predicted when it said CSM's risk had moved
from ontology incompleteness to boundary clarity.

**Run the control.** Without it, "2 of 14 agreed" reads as *downscaling wrecks
recognition*, and a workable proposal dies on a number that means nothing on its
own.

## Open, decided, not yet built

- **[COS-53]** — approved. Recognition may read a stored DERIVED asset when the
  original is large, provided the original is still stored in full. The
  machinery exists and points the other way: `startNonBlockingDerivedUpload`
  already uploads derived images without blocking while originals block. Rule:
  use the derived image **only when it is actually smaller** — re-encoding a
  237KB webp to 1600px JPEG produced 478KB.
- **[COS-56]** — approved. Product > Set > Card Name precedence, with Card Name
  EMPTY when the printed phrase is exhausted by Product and Set. Baseline to
  beat: 21 disagreements / 14 cards / 4-of-14 agreeing, on identical inputs.

Do COS-56 first: it addresses accuracy, and that loss is structural — a field
that oscillates is wrong on a share of runs by construction, and no model or
pipeline work removes it.

  comparison, no labels needed. `--control` gives both arms the original and is
  the reason any of its numbers can be read. `--per-card 1` for singles.

## Environment notes

- macOS TCC blocks `/Users/*/Desktop`. Copy inputs to `/tmp` first.
- `api.openai.com` needs `NODE_USE_ENV_PROXY=1`; the proxy is at
  `HTTPS_PROXY=http://127.0.0.1:7897`. Node's fetch ignores it otherwise and
  resolves to a hijacked address.
- The PostgreSQL harnesses supply `LC_ALL=C` themselves now. Do not remove it.
